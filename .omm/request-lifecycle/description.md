How one HTTP request travels through the NestJS API, and how the Socket.IO channel differs. REST order, as wired in main.ts, setup-app.ts, app.module.ts and auth.module.ts: (1) nginx/Caddy forwards /api/* to api:3000; (2) Express middleware: helmet headers, MetricsMiddleware (route timing), TenantMiddleware (AsyncLocalStorage.run({}) for the rest of the request); (3) global guards in order RateLimitGuard -> JwtAuthGuard -> RolesGuard; (4) global AuditInterceptor; (5) global ValidationPipe (whitelist, forbidNonWhitelisted, transform) plus per-param pipes such as ParseUUIDPipe; (6) controller -> service -> PrismaService.db, whose tenant extension injects universityId; (7) on success the AuditInterceptor writes an AuditEvent for office/super_admin mutations; (8) any exception goes to the global SentryExceptionFilter, which reports 5xx/unknown errors to Sentry and lets Nest's BaseExceptionFilter build the JSON response. WebSocket clients instead connect to namespace /live, authenticate once in the handshake and talk through gateway message handlers.
